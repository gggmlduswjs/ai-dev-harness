# 1. Linear와 GitHub 이슈 활용법

> **목적:** 작업을 어디서 관리하고, 코드와 문서는 어디에 두며, 둘을 어떻게 연결하는지 정합니다. Linear를 처음 쓰는 사람도 이 문서대로 설정하고 쓸 수 있게 씁니다.


## 1. 한 장 요약

| 도구 | 맡는 것 | 맡지 않는 것 |
|---|---|---|
| **Linear** | 무엇을·언제·어떤 순서로 — Project, Milestone, Issue, 상태, 우선순위, 목표일, 의존성 | 긴 설계·명세·결정 근거 |
| **Repository(`docs/`)** | 제품과 기술의 공식 지식 — PRD, 설계서, ADR, 업무 규칙 | 진행 상태, 우선순위, 일정 |
| **GitHub** | 코드, 브랜치, PR, CI, 머지 이력 | 작업 계획과 진행 관리 |
| **GitHub Issues** | (선택) **외부 사용자의 신고·제안을 받는 창구** | 내부 작업 관리 |

흐름은 이렇게 이어집니다.

```text
Linear 이슈 → 브랜치(BOO-123) → PR → CI → 승인된 머지 → 증거 확인 → Linear Done
                  ↑                                                     │
        이슈에 Repo 경로(설계서·ADR) 링크          끝난 뒤 정본으로 승격(CONVENTIONS 6장)
```

## 2. GitHub Issues를 쓸까, Linear만 쓸까

**기본은 Linear 하나입니다.** 같은 작업이 두 곳에 있으면 정본이 둘이 됩니다.

| 상황 | 선택 |
|---|---|
| 혼자 또는 팀 내부 프로젝트, 외부 신고를 받지 않음 | **Linear만.** GitHub 레포의 Issues 기능은 끄거나 비워 둡니다. |
| 공개 프로젝트라 외부 사용자가 버그를 신고함 | GitHub Issues를 **접수 창구**로 두고(아래 6장), 받아들인 것만 Linear 이슈로 만들어 링크합니다. |

참고 사례: Saleor는 외부 버그·기능 제안을 GitHub Issues로 받고, 내부 작업은 Linear로 관리합니다. PR 본문에 Linear 이슈 링크가 붙어 있습니다(2026-10-02 `gh`로 확인).

## 3. Linear 구조 — 이 틀과 이어 붙이기

```text
팀(Team)            키가 이슈 번호 접두어가 됨 (예: BOO-123)
 └─ 프로젝트        = ROADMAP의 단계 하나
     └─ 마일스톤    = 그 단계의 완료 기준 묶음
         └─ 이슈    = PR 하나로 끝나는 작업
```

| Linear | 이 틀 | 만드는 시점 |
|---|---|---|
| Project | `docs/ROADMAP.md`의 단계 | 새 프로젝트 시작(`0-start-project.md` 7단계) |
| Milestone | 그 단계의 "완료 기준" | 단계를 시작할 때 |
| Issue | `templates/LINEAR_ISSUE.md` | 작업 하나마다 |

- 팀은 **처음엔 하나**로 충분합니다. 제품이 둘 이상이면 프로젝트 이름 앞에 `[제품명]`을 붙입니다.
- **긴 문서는 Linear에 복사하지 않고 Repo 경로를 링크**합니다.
- Linear 문서(Documents)에는 개요 한 장 정도만 둡니다. 정본은 `docs/`입니다.

## 4. 상태(Status) — 정의를 정해서 쓴다

상태 이름만 있으면 사람마다 다르게 씁니다. **상태마다 "들어오는 조건"과 "필요한 증거"**를 정합니다.

| 상태 | 들어오는 조건 | 필요한 증거 |
|---|---|---|
| Backlog | 아이디어·발견 사항. 우선순위 미정 | 없음 |
| Todo | 우선순위를 정했고 **다음에 할 일** | 우선순위 지정 |
| In Progress | 지금 만들고 있음 | 브랜치가 있음 |
| In Review | PR을 올렸고 검토 중 | PR 링크 |
| **Merged** | PR이 머지됨 | 머지 커밋 |
| Deployed | 운영에 반영됨 | 배포 기록 |
| **Done** | 완료 조건(AC)을 **증거로 확인**함 | AC별 증거(테스트 결과, 재조회, 화면 확인) |
| Canceled / Duplicate | 하지 않기로 함 / 중복 | 사유 한 줄 |

- Linear의 기본 상태에는 `Merged`·`Deployed`가 없습니다. **`Merged`를 추가하는 것을 권장합니다.** 머지와 "다 됐다"를 분리해야 `Done`이 증거 확인 뒤에만 찍힙니다.
- **`Done`은 AC 증거와 실제 머지를 확인한 뒤에만** 합니다. 상태 변경은 승인을 대신하지 않습니다.

### 동시에 진행하는 개수

- **PR 하나짜리 작업은 동시에 최대 1~3개**만 In Progress로 둡니다.
- 길게 이어지는 **검증·연구 같은 "트랙"**은 작업과 구분합니다(라벨 `track`). 트랙은 마일스톤 완료 기준을 재는 과정이라 이 상한에 넣지 않습니다.
- 급하지 않은 발견은 현재 작업에 몰래 넣지 말고 **Backlog에 새 이슈**로 보냅니다. 운영 장애만 현재 작업을 멈출 수 있습니다.

## 5. 이슈 쓰는 법

### 제목
**결과 문장**으로 씁니다. `관리자가 중복 업체를 합치고 결과를 확인한다`처럼 "누가 무엇을 한다"입니다. 종류나 마일스톤 코드(`[1A]` 등)는 제목에 넣지 않고 라벨과 마일스톤 칸에 둡니다.

### 본문
[`templates/LINEAR_ISSUE.md`](../../templates/LINEAR_ISSUE.md) 양식을 씁니다. 핵심은 네 가지입니다.

1. **기대 결과** — 끝나면 무엇이 달라지나
2. **완료 조건(AC)** — 체크할 수 있는 문장으로
3. **관련 맥락** — 설계서·ADR·도메인 문서의 **Repo 경로**
4. **제외할 것** — 이번에 하지 않는 것

진행 상태, 우선순위, 목표일, 의존성은 **본문에 쓰지 않고 Linear 속성**으로 둡니다.

### 크기
**PR 하나로 끝나는 크기**로 자릅니다. 며칠이 걸리거나 여러 PR이 필요하면 하위 이슈로 쪼개거나 마일스톤으로 올립니다.

### 라벨 — 두 축
| 축 | 값 | 목적 |
|---|---|---|
| **종류** | Feature · Improvement · Bug · 구조 · 조사 · 결정 · track | 무엇을 하는 일인가 |
| **도메인** | 코드의 도메인 폴더 이름과 **같게**(`orders`, `inventory` …) | 어느 업무인가 |

폴더 → 문서 → 이슈 → 라벨이 같은 이름으로 이어져서 검색과 필터가 쉬워집니다.

### 우선순위
Urgent / High / Medium / Low. **Backlog는 미지정이어도 되지만 Todo 이상은 반드시 지정**합니다.

## 6. GitHub Issues를 접수 창구로 쓸 때 (공개 프로젝트)

외부 신고를 받는 경우에만 설정합니다. Saleor의 운영 방식에서 가져온 것입니다.

| 장치 | 설정 |
|---|---|
| 빈 이슈 금지 | `.github/ISSUE_TEMPLATE/config.yml`에 `blank_issues_enabled: false` |
| 질문은 이슈가 아님 | 같은 파일의 `contact_links`로 GitHub Discussions 안내 |
| 버그 양식 | 무엇을 하려던 건지, **재현 단계**, 기대 동작, 로그, 환경 |
| 기능 요청 양식 | 문제, 가정, 완료 조건. 논의를 먼저 거치게 함 |
| 큰 변경 | Discussions에서 설계 제안(RFC)을 먼저 받음 |

**접수 → Linear로 옮기는 규칙:** 받아들인 신고는 Linear 이슈를 만들고, GitHub 이슈에 Linear 이슈 ID를 코멘트로 남깁니다. 이후 진행 상태는 Linear에서만 관리합니다.

## 7. GitHub와 연결하기

1. Linear 설정의 **Integrations**에서 GitHub를 연결합니다(저장소 접근 권한 필요).
2. **브랜치 이름에 이슈 ID를 넣습니다.** Linear가 이슈마다 브랜치 이름을 만들어 줍니다(이슈 화면에서 복사).
3. **PR 제목이나 본문에 이슈 ID**를 넣습니다. PR 양식의 `Linear:` 칸을 채웁니다.
4. PR이 머지되면 이슈를 `Merged`로 옮깁니다(연동이 자동으로 옮기는지는 설정에 따라 다르니, 먼저 한 건으로 확인하세요).
5. `Deployed`와 `Done`은 증거를 확인하고 **직접** 옮깁니다.

## 8. Repo와 Linear를 서로 가리키기

- **이슈 → Repo:** 이슈 "관련 맥락"에 설계서·ADR·도메인 문서의 경로를 적습니다.
- **Repo → 이슈:** 설계서·계획서 맨 위 라벨의 `linear:` 칸에 이슈 ID를 적습니다.
- 내용은 **한 곳에만** 있습니다. 같은 문장을 양쪽에 복사하지 않습니다.
- 작업이 끝나면 앞으로도 유효한 것을 정본으로 올립니다([CONVENTIONS](../CONVENTIONS.md) 6장).

## 9. 저장 뷰(Views) — 매번 찾지 않게

| 뷰 | 조건 | 쓰는 때 |
|---|---|---|
| 지금 | 내가 담당, 상태 In Progress | 하루 시작 |
| 다음 | Todo, 우선순위순 | 다음 작업 고르기 |
| Backlog 정리 | Backlog, 우선순위 미지정 | 주 1회 |
| 증거 대기 | 상태 Merged | Done 처리 전 점검 |

## 10. 하루 흐름 (처음 쓰는 사람용)

1. **My issues**를 엽니다. 오늘 할 이슈가 여기 있습니다.
2. 이슈 하나를 `In Progress`로 옮기고, 이슈 화면의 브랜치 이름으로 작업합니다.
3. 막히거나 모르는 것이 중요하면 조사 이슈를 따로 만듭니다.
4. PR을 올리고 `In Review`로 옮깁니다.
5. 머지되면 `Merged`로 옮기고, AC를 증거로 확인한 뒤 `Done`으로 옮깁니다.
6. 작업 중 발견한 다른 문제는 **새 이슈를 Backlog에** 만듭니다.

## 11. 처음 설정 체크리스트

- [ ] 팀을 만들고 키(예: `BOO`)를 정했다
- [ ] 상태에 `Merged`를 추가하고 위 표대로 정의를 정했다
- [ ] 라벨: 종류 7개 + 도메인(코드 폴더 이름)
- [ ] 이슈 템플릿(기능·버그·구조)을 만들었다 — 본문은 `templates/LINEAR_ISSUE.md`
- [ ] 저장 뷰 4개를 만들었다
- [ ] GitHub를 연결했다
- [ ] 프로젝트·마일스톤을 `docs/ROADMAP.md`와 맞췄다

## 12. 알아둘 점

- Linear의 **Releases**(CI/CD로 어느 이슈가 어느 릴리스에 나갔는지 추적)와 **Loops**(자동화, AI 크레딧 소모)는 **요금제에 따라 제한**됩니다(2026-10-02 Linear 문서 기준). 이 문서의 방식은 기본 기능만으로 됩니다.
- GitHub Issues·Jira·Asana·Shortcut에서 가져오는 **가져오기(Import) 도구**가 Linear에 있어서, 기존 이슈가 있으면 옮길 수 있습니다.
