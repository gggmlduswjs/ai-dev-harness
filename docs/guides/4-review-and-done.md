# 4. 리뷰와 완료 판단

> **목적:** AI가 "다 했습니다"라고 말했을 때 **무엇을 확인해야 진짜 끝인지**, 리뷰에서 찾은 문제를 **얼마나 급하게 다룰지**를 정합니다.
> 이 틀의 원칙 5번("AI가 완료했다고 말하는 것만으로 완료 처리하지 않는다")을 구체적인 표로 만든 문서입니다.

## 1. 완료는 4단계로 구분합니다

PR 설명과 Linear 코멘트에서 **같은 말을 같은 뜻으로** 쓰기 위한 어휘입니다.

| 상태 | 뜻 | 확인 방법 |
|---|---|---|
| 작성됨 | 코드가 써졌다 | diff가 있다 |
| 테스트됨 | 자동 테스트가 통과했다 | 테스트 명령과 결과를 PR에 붙임 |
| 동작함 | 실제 환경(로컬 서버·브라우저·스테이징)에서 돌려 봤다 | 화면 캡처, 로그, 응답 |
| 검증됨 | 외부 시스템 재조회나 운영 지표로 결과를 확인했다 | Evidence 링크·조회 결과 |

**"작성됨"만 말하고 "완료"라고 하지 않습니다.** Linear의 `Done`은 위험도에 맞는 단계까지 확인한 뒤에만 옮깁니다(작은 수정은 "테스트됨", 외부 연동·결제·데이터 변경은 "검증됨").

## 2. 완료 조건은 명령으로 확인할 수 있게 씁니다

Linear 이슈의 완료 조건(AC)과 계획서의 단계마다, **실행하면 통과/실패가 나오는 명령이나 조회**를 함께 적습니다.

| 나쁜 예 | 좋은 예 |
|---|---|
| 로그인이 잘 된다 | `pytest tests/auth -q`가 통과하고, 잘못된 비밀번호는 401을 돌려준다 |
| 목록이 빨라진다 | `/api/items` 응답이 200개 기준 300ms 이하(측정 명령 첨부) |

만드는 쪽(구현 AI)과 확인하는 쪽(리뷰 AI 또는 나)은 **가능하면 분리**합니다. 같은 세션이 만들고 같은 세션이 "문제없다"고 하면 검증이 아닙니다.

## 3. 리뷰 심각도와 행동 규칙

리뷰 결과(사람이든 AI든)는 아래 4단계로 분류하고, 단계마다 **하는 일이 정해져 있습니다.**

| 심각도 | 예 | 행동 |
|---|---|---|
| **치명** | 인증 우회, 데이터 유실, 시크릿 노출 | 머지 금지. 즉시 수정하고 원인을 기록 |
| **높음** | 하위 호환 깨짐, 마이그레이션 누락, 테스트 없는 위험 변경 | 머지 전에 수정 |
| **중간** | 기존 패턴과 다른 구현, 불필요한 범위 확대 | 수정하거나, 남기는 이유를 PR에 적음 |
| **낮음** | 이름·주석·정리 | 선택. Linear Backlog로 보내도 됨 |

- AI 리뷰의 **오탐은 규칙 한 줄로 막습니다**(예: "이 폴더는 생성 코드라 검사하지 않는다"). 같은 오탐을 매번 사람이 걸러 내지 않습니다.
- 리뷰 결과는 **한눈에 보는 요약 + 줄별 코멘트** 두 층으로 받습니다. 요약에는 심각도별 개수와 머지 가능 여부를 먼저 적게 합니다.
- 리뷰 점검 항목: 수정 범위, 기존 패턴, 테스트, 리스크([2번 가이드](2-daily-loop-and-second-brain.md) 5장). **삭제된 코드는 따로 한 번 더 봅니다.** AI는 이유 없이 지우는 실수를 자주 합니다.

## 4. 작업 크기에 따른 확인 수준

| 크기 | 예 | 최소 확인 |
|---|---|---|
| 작은 수정 | 문구·스타일·내부 정리 | 테스트 통과 + diff 확인 |
| 기능 | 새 화면·API | 계획서 승인 → 테스트 → PR 리뷰 → 동작 확인 |
| 운영 변경 | 결제·인증·개인정보·데이터 마이그레이션·외부 연동 | 위 전부 + 되돌리는 방법 + 검증됨 단계 + 배포 전 확인(5장) |

## 5. 배포 전 확인 (운영에 나가는 변경)

아래 다섯 가지 중 **하나라도 해당되면** PR에 확인 결과를 적습니다.

- [ ] 외부에서 접근할 수 있는 주소·API를 새로 열었나
- [ ] 결제나 돈이 오가는 흐름을 건드렸나
- [ ] 개인정보를 읽거나 저장하나
- [ ] 되돌리기 어려운 동작(삭제·일괄 변경·외부 전송)이 있나
- [ ] 시크릿(키·토큰)을 코드·로그·설정에 넣지 않았나

## 6. 반복되는 일은 자산으로 올립니다

| 신호 | 올릴 곳 |
|---|---|
| 같은 일을 AI에게 **3번** 시켰다 | 스킬(gg-tools에 추가, 이 레포에는 두지 않음) |
| 같은 실수를 AI가 **3번** 했다 | 규칙(`CLAUDE.md` 또는 `.claude/rules`) |
| AI에게 못 맡기겠다고 느꼈다 | 원인을 먼저 나눈다: 맥락이 부족했나, 도구가 없었나, 검증 수단이 없었나 → 그 부분만 보강 |
| `CLAUDE.md`가 200줄을 넘는다 / 낡은 규칙이 있다 | 줄이거나 `docs/`로 링크하고, 낡은 항목은 지움 |

## 7. 하지 않는 것 (지금 규모에서는 과함)

- 야간 자동 머지, 사람 승인 없는 배포
- 상시 동작 에이전트(서버에서 24시간), 당직 에이전트, 조직 단위 롤아웃
- 이 문서의 표를 hook으로 자동 강제하는 것은 필요해지면 gg-tools에 추가합니다.

## 8. 브라우저 검수

화면 또는 사용자 조작을 바꾼 작업은 관련 자동 테스트 후 실제 구현 화면을 확인합니다. 기본 도구는 [Playwright MCP](https://github.com/microsoft/playwright-mcp), 연결 방법은 [새 PC 가이드](00-new-pc-setup.md#브라우저-검수-도구-연결)입니다. 프로젝트가 정한 화면·권한·업무 기준을 우선하며 이 절은 Claude·Codex에 공통으로 적용합니다.

1. **대상 확인:** 브랜치·URL·역할·데이터 출처와 서버의 실제 API/DB 연결을 확인합니다. localhost라는 이유만으로 테스트 데이터라 판단하지 않습니다. 저장·삭제·발송 흐름은 격리된 테스트 환경에서 확인하고 운영 write는 별도 승인 계약을 따릅니다.
2. **화면 관찰 → 조작 → 결과 확인:** `browser_snapshot`으로 현재 요소를 찾고 실제 클릭·입력·조회·초기화·저장·취소를 수행합니다. 변경한 흐름의 기대값과 화면·응답을 대조하며 새 상태를 읽고 다음 조작을 합니다. 예시 응답만으로 서버 로직이 검증됐다고 하지 않습니다.
3. **상태·키보드·화면 크기:** 관련 로딩·빈 결과·오류·권한 상태, 긴 글자, Tab/Enter/ESC와 포커스 복귀를 확인합니다. 프로젝트 기준 크기로 `browser_resize` 후 실제 viewport 치수를 읽습니다. 요청한 크기와 다르면 미검증으로 기록하고 종료 시 임시 크기를 복원합니다.
4. **개발자 검사:** `browser_console_messages`와 `browser_network_requests`로 새 오류, 실패 응답, 중복 요청을 확인합니다. 필요한 요청만 열어 필터·수량·대상·응답을 대조합니다. 쿠키·토큰·개인정보가 든 원본 로그를 PR에 올리지 않습니다.
5. **결과 기록:** URL·브랜치/커밋·역할·데이터 출처·실제 viewport·조작/기대값/관찰값·콘솔/네트워크 결과·캡처·미검증 이유를 기존 PR 또는 Issue에 남깁니다. 발견은 재현과 코드로 확인하고 관련 수정 뒤 그 시나리오를 다시 확인합니다. 새 검수 장부·실행기는 만들지 않습니다.

같은 탭을 여러 AI가 동시에 조작하지 않습니다. 다른 브라우저 도구를 쓸 때도 위 검수 기준을 적용하고, 현재 런타임이 지정한 브라우저 도구/API 제한을 지킵니다. MCP가 없거나 실행이 막히면 가능한 도구로 확인한 범위와 미검증 항목을 구분합니다. 연결 확인이나 자동 테스트 통과가 사람의 화면 수락·merge·배포 승인을 대신하지 않습니다. 검수 뒤 임시 서버·브라우저는 종료하고, 사용자가 열어 둘 것을 요청한 화면만 인계합니다.
