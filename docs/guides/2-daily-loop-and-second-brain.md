# 2. 하루 루프와 세컨드 브레인

> **목적:** 이 레포를 받은 뒤 **채팅으로 말하면서 바로 개발**하는 일상 방식을 정합니다. 스킬과 hook은 이 레포에 복사하지 않고 **gg-tools 플러그인에서 가져다 씁니다**(소유권은 [gg-tools README](https://github.com/gggmlduswjs/gg-tools#자산-소유권--먼저-여기서-확인) 기준).
> 일반적인 AI 개발 방식에서 이 틀에 필요한 것만 골랐습니다.

## 1. 한 줄 원칙

**기획·실행은 AI가, 범위·중요한 결정·운영 승인은 사람이 판단합니다.**
프로젝트가 정한 AI 역할을 우선합니다. 별도 지정이 없을 때 기본은 Claude 기획 + Codex 구현이며, Claude executor·Codex 단독·companion 위임도 같은 승인·인계·검증 계약을 따릅니다. PRD·ROADMAP·ARCHITECTURE와 필요한 설계서·계획서는 사람이 승인합니다. 이미 승인된 범위의 실행은 이어서 수행하고, 머지·운영 변경 승인은 구현 승인과 구분합니다.

## 2. 하루 루프

| 시간 | 하는 일 | 쓰는 것 |
|---|---|---|
| 아침 | 오늘 할 일 파악 | Linear 뷰 **지금**·**다음**, 아래 브리핑 프롬프트 |
| 낮 | 이슈 하나의 범위 확인 → 승인된 작업 구현 → 관련 검증. 중요한 불확실성에는 조사, 복잡하거나 고위험인 작업에는 설계·계획 추가 | 아래 작업 절차와 필요한 Superpowers 스킬 |
| 낮 | 결과를 검수하고 재지시 | 계획 검토 4체크(5장), 테스트, PR diff |
| 저녁 | 한 일·못한 일·개선점 정리 | Linear 뷰 **증거 대기**, 세컨드 브레인 기록(4장) |

**브리핑 프롬프트** (스킬 없이 그대로 붙여 쓰는 한 줄 요청):

```text
Linear에서 내게 할당된 이슈 중 In Progress와 Todo를 우선순위순으로 정리해줘.
머지 안 된 PR과 main의 CI 상태도 확인해서, 오늘 꼭 할 일과 안 해도 될 일을 나눠줘.
```

반복해서 길어지면 그때 gg-tools에 스킬로 올립니다(이 레포에는 두지 않음).

### 작업 절차

이 절이 **Claude·Codex 역할 분담과 Codex 단독 실행의 정본**입니다. Superpowers는 작업 방법을 제공하고, `codex-plugin-cc`는 Claude Code에서 Codex에 작업을 넘기는 연결 도구입니다. 이 하네스는 정본·인계·승인·완료 기준을 정합니다. 별도 실행기나 두 번째 작업 보드는 만들지 않습니다.

| 실행 방식 | 기획·조사·범위 및 계획 정리 | 구현·관련 검증 | 결과 검수 |
|---|---|---|---|
| 프로젝트 지정 역할(우선) | 프로젝트의 AGENTS/CLAUDE 계약에 따른 담당 AI | 지정 실행 AI(Claude executor 등) | 프로젝트가 정한 검수와 승인 |
| 별도 지정이 없을 때 기본 분업 | Claude + 필요한 Superpowers 스킬 | Codex (`/codex:rescue`로 위임) | Claude 또는 사람이 계약·diff·실행 근거 확인 |
| Codex 단독 | Codex + 사용 가능한 Superpowers 스킬 | Codex를 직접 사용 | Codex가 계약·diff·fresh 검증 결과를 확인하고 사람이 중요한 판단·승인 |
| Claude 한도 소진 후 전환 | 기존 기획·승인 범위를 Codex가 재확인하고 미결정 부분만 보완 | 같은 작업 브랜치·worktree에서 Codex가 계속 수행 | Codex 단독과 같은 기준 |

#### 범위 확인과 승인

1. 수행 AI가 `AGENTS.md`, 루트·대상 계층의 `CLAUDE.md`, 현재 요청/Issue의 연결 문서와 관련 코드·기존 Research/Plan을 먼저 확인합니다. 중요한 정보가 부족하거나 중복 작업 가능성이 있을 때만 탐색을 넓힙니다. 브랜치·worktree·사용자 WIP도 확인합니다.
2. **작은 수정·범위가 명확한 작업**은 목표·완료 조건·제외 범위·검증 방법을 요청이나 Issue에서 확정하고 바로 구현합니다. 사용자가 해당 수정을 이미 요청·승인했다면 같은 범위를 다시 승인받지 않습니다. 별도 Research·Spec·Plan은 강제하지 않습니다.
3. **중요한 불확실성**은 Research, **복잡하거나 고위험인 변경**은 필요한 설계·계획을 추가합니다. 프로젝트가 정한 작성자가 맡으며, 별도 지정이 없으면 분업에서는 Claude, 단독에서는 Codex가 작성합니다. Superpowers `brainstorming`·`writing-plans`를 사용하되 산출물 위치는 루트 `CLAUDE.md`를 따릅니다. 구현 전 사람이 필요한 설계·계획을 승인합니다.
4. 새로운 제품 결정, 승인 범위를 넘는 변경, 운영 write·머지 등 별도 승인이 필요한 행동은 확인합니다. 계획에 포함된 코드 수정을 승인했다고 운영 변경까지 승인된 것으로 해석하지 않습니다.

#### 실행 AI가 바로 이어받을 수 있는 인계

계획이 있는 작업은 **프로젝트의 기존 계획서에 실행 인계 절**(`Codex 인수인계` 등)을 둡니다. 별도 경로 규칙이 없으면 `.dev/plans/`를 씁니다. 목표·완료 조건, 승인 범위, 관련 정본, 작업 디렉터리·브랜치·변경 파일, 검증 근거, 미해결 질문을 짧게 적고, 재사용 함수·의존성·금지 범위는 기존 계약에 연결합니다. 승인 근거는 실제 사용자 지시나 관련 Issue에 연결하며 문서의 `status`만으로 승인됐다고 판단하지 않습니다. 새 인계 문서나 별도 실행 계획으로 다시 번역하지 않습니다.

작은 작업은 요청/Issue의 짧은 지시로 충분합니다. AI 교체·한도 소진 시에는 5장의 인계문을 사용하고, 승인된 결정을 다시 설계하지 않습니다. 기존 계약과 실제 코드가 충돌하거나 필수 정보가 빠졌으면 그 부분만 확인합니다.

**Claude Code 안에서 위임할 때**는 프로젝트 기준으로 정한 현재 작업 디렉터리(저장소 또는 worktree)에서 실행합니다. 새 작업은 `--fresh`, 같은 Codex 작업의 후속은 `--resume`으로 구분합니다. 아래 경로는 실제 승인된 계획서로 바꿉니다.

```text
/codex:rescue --fresh --background .dev/plans/YYYY-MM-DD-기능명.md의 Codex 인수인계에 따라 구현·검증해줘. AGENTS.md와 CLAUDE.md를 먼저 읽고 승인 범위를 지켜줘.
/codex:status
/codex:result
/codex:rescue --resume --background 앞서 승인한 같은 작업의 미완료 구현·검증을 이어서 수행해줘.
```

`/codex:rescue`는 명시적 구현 요청이면 쓰기 가능한 작업을 위임하고, 조사·리뷰만 요청하면 읽기 전용으로 전달합니다. 전달용 subagent는 작업을 직접 풀지 않는 플러그인의 forwarder입니다. `/codex:result`의 출력은 플러그인 계약대로 보존하며, 별도 검수에서 diff와 실제 실행 근거를 확인합니다. 연결·인증이 안 되어 있으면 `/codex:setup`으로 확인합니다. 설치·명령 정본은 [codex-plugin-cc](https://github.com/openai/codex-plugin-cc)이며, 엔진·명령 본문을 이 레포에 복사하지 않습니다.

**Codex를 직접 사용할 때**는 해당 저장소/worktree를 열고 아래처럼 요청합니다. Claude의 실행이나 `codex-plugin-cc` 호출이 필요하지 않습니다.

```text
AGENTS.md와 루트·대상 계층 CLAUDE.md를 읽고, .dev/plans/YYYY-MM-DD-기능명.md의 승인된 Codex 인수인계를 구현·검증해줘. 현재 브랜치와 사용자 WIP를 확인하고, 승인된 결정은 유지해줘.
```

계획이 없는 작은 작업은 계획서 경로 대신 목표·완료 조건·제외 범위를 적습니다. Codex 단독으로 새 기획부터 시작할 때는 구현 전 필요한 범위·설계·계획을 사용자와 확정합니다. 런타임에 스킬이 없으면 이름을 호출했다고 가정하지 않고 같은 조사·구현·검증 절차를 수행하며, 사용할 수 없는 도구와 검증은 보고합니다.

#### 구현·검수·마무리

- 프로젝트가 지정한 실행 AI가 승인된 계약을 직접 실행하고 프로젝트의 TDD·디버깅·검증 규칙을 따릅니다. 같은 작업의 브랜치·worktree·PR을 재사용하고 같은 파일을 두 AI가 동시에 수정하지 않습니다. Worktree를 언제 만들고 어디에 두며 언제 회수할지는 프로젝트 기준을 우선합니다. 위임 도구를 쓴다는 이유만으로 새 worktree를 만들지 않습니다.
- 결과에는 변경 파일·재사용 근거·검증 명령과 결과·생략한 검증과 이유·남은 리스크를 남깁니다. `AGENTS.md`의 완료 구분을 따릅니다.
- 프로젝트의 검수 역할을 우선하며, 별도 지정이 없으면 분업은 Claude 또는 사람, Codex 단독은 Codex와 사람이 계약·diff·fresh command output·CI를 확인합니다. 독립 AI 리뷰는 복잡하거나 고위험인 작업에 추가하고 같은 diff의 리뷰를 자동으로 중복하지 않습니다. Codex 단독 구현·자체 확인은 독립 리뷰로 부르지 않습니다.
- Claude Code의 `/codex:review`는 읽기 전용 리뷰입니다. 리뷰에서 나온 수정은 적용할 항목·범위를 승인한 뒤 별도 구현 요청으로 넘깁니다. 선택적인 stop review gate는 필수 절차가 아니며, 이 문서가 사용자 설정을 자동 변경하지 않습니다.
- PR 전에 필요한 정본을 같은 변경에 반영합니다([CONVENTIONS](../CONVENTIONS.md) 6장). 머지·배포·운영 적용은 해당 프로젝트의 명시 승인 규칙을 따르고, AC 증거와 필요한 병합·운영 근거를 확인한 뒤 Linear Done으로 옮깁니다. 판단 기준은 [4번 가이드](4-review-and-done.md)입니다.

## 3. 처음 한 번 설정 — 플러그인 연결

**Team Plugin**(스킬·hook·명령을 한 묶음으로 배포하는 단위)이 우리에게는 [gg-tools](https://github.com/gggmlduswjs/gg-tools)의 `gg-skills` 플러그인입니다. 이 레포 `.claude/settings.json`은 **어떤 플러그인을 쓰는지 선언**만 합니다(superpowers, gg-skills). 스킬 파일은 레포에 없습니다. `codex-plugin-cc`를 포함한 설치 목록은 gg-tools가 관리하며, 실제 전역·프로젝트 활성 설정을 확인합니다. Codex 단독에서는 Claude 전용 hook·명령이 실행된다고 가정하지 않습니다. 새 PC에서는 한 번만 실행합니다.

```powershell
gh repo clone gggmlduswjs/gg-tools ~/claude
pwsh ~/claude/bootstrap.ps1
```

이후 Claude Code를 새 세션으로 열면 됩니다. 자동 검사 hook(위험 명령 차단)의 shim은 [`.claude/hooks/guardrail.py`](../../.claude/hooks/guardrail.py)이고, 판정 로직은 gg-tools 엔진 한 벌입니다. 엔진이 없는 PC에서는 조용히 통과하지 않고 **확인을 요청**합니다(보호가 꺼진 것을 숨기지 않기 위해).

| 하고 싶은 것 | 쓰는 것 (gg-skills) |
|---|---|
| 틀을 적용한 뒤 AI가 코드를 잘 이해하는지 점수 | `ai-readiness-cartography` |
| 하네스 빈칸 점검 | `harness-audit` |
| 토큰·비용 점검 | `improve-token-efficiency` |
| 보안 점검 | `owasp-security-scan` |
| 세컨드 브레인 (선택) | gg-tools의 `wiki-ingest` · `wiki-query` · `wiki-lint` (Codex 사용은 4장) |

## 4. 지식이 사는 곳 — 세컨드 브레인

세컨드 브레인에 **기준 문서를 두면 정본이 하나 더 생깁니다.** 그래서 층을 나눕니다.

| 층 | 담는 것 | 정본인가 |
|---|---|---|
| Repo `docs/` | 제품·설계·결정·업무 규칙 | **예 (지식)** |
| Linear | 진행·우선순위·일정 | **예 (실행)** |
| 자동 메모(Auto-memory) | AI에게 알려 준 개인 선호 | 개인용 |
| 세컨드 브레인 (`second-brain` 레포) | 여러 프로젝트에서 재사용하는 일반 지식, 강의·조사 요약 | **아니오.** 프로젝트 정본을 링크만 함 |

팀이 공유할 규칙은 `CLAUDE.md`, 개인 선호는 자동 메모입니다.

**승격:** 세컨드 브레인의 메모가 프로젝트에 유효해지면 `.dev/research/` → `docs/` 순으로 올립니다([CONVENTIONS](../CONVENTIONS.md) 6장). **복사하지 말고 한 곳으로 옮기고 링크**합니다.

### 어디에 두나 — 별도 비공개 레포 `second-brain`

| 지식의 종류 | 자리 |
|---|---|
| 한 프로젝트에서만 쓰는 지식 | **그 프로젝트의 정본 자리**(보통 그 프로젝트 레포의 `docs/`). 정본이 레포 밖(예: 별도 문서 폴더)에 있으면 그 자리를 그대로 존중하고, 여기로 복사하지 않음 |
| 여러 프로젝트에서 다시 쓰는 일반 지식 | **`second-brain` 레포** (GitHub 비공개, 로컬 `~/second-brain`) |
| AI가 건드리지 않는 개인 노트(일정, 인박스, 공부) | 구글 드라이브 Obsidian |

구글 드라이브에는 변경 이력이 없고 동기화 지연·충돌이 있어서, 새로 쌓는 AI 위키는 **git 레포**에 둡니다. Obsidian은 이 폴더를 볼트로 열면 됩니다. 같은 지식이 여러 곳에 있으면 정본이 둘 생기므로, 위 표의 첫 줄(프로젝트 전용은 프로젝트 정본)을 먼저 지킵니다. 낡은 위키는 지우지 않고 `_archive/`로 보관하며 근거로 쓰지 않습니다.

### 구조 (3층)

gg-tools가 배포하는 `wiki-*` 스킬이 사용하는 구조이고(빈 틀은 [wiki-template](https://github.com/gggmlduswjs/wiki-template) 저장소의 **Use this template**로 만듭니다), 프로젝트 안에 둔 위키도 같은 구조를 쓰면 같은 스킬이 동작합니다.

```text
second-brain/
├── WIKI_SCHEMA.md   ← 규칙: 파일명·프론트매터·본문 틀·Ingest/Query/Lint   (Schema, 스킬이 가장 먼저 읽음)
├── raw/             ← 원문. 사람이 넣고 수정하지 않음                      (Raw)
├── wiki/
│   ├── index.md     ← 카탈로그 (페이지마다 한 줄 요약)
│   ├── log.md       ← 추가만 하는 기록 ([INGEST] [QUERY] [LINT] [MOVE])
│   └── concepts/ people/ tools/   ← 페이지, [[링크]]로 연결
└── _archive/        ← 낡은 기록
```

- **넣기:** 원문을 `raw/`에 두고 "위키에 넣어"라고 하면 `wiki-ingest`가 통합하고 `index.md`·`log.md`를 갱신합니다.
- **묻기:** "위키에서 찾아"라고 하면 `wiki-query`가 `[[페이지]]`를 인용해 답합니다.
- **점검:** 가끔 `wiki-lint`로 모순·고아 페이지·깨진 링크를 찾습니다(고치기 전에 승인).
- 마크다운과 `[[링크]]`를 쓰므로 Obsidian으로 열어 볼 수 있습니다.

> 첫 Ingest는 `SKILL.md` 절차대로 수동으로 시험해 통과했습니다(페이지 3개, 깨진 링크 0). 스킬 자동 호출은 새 세션에서 따로 확인합니다. 스킬은 폴더를 만들지 않으므로 위키 폴더(`WIKI_SCHEMA.md`가 있는 곳)에서 Claude Code를 열어 시작합니다.

### Codex에서 위키 스킬 사용

`wiki-ingest`·`wiki-query`·`wiki-lint`는 `WIKI_SCHEMA.md`와 Markdown 파일을 읽고 쓰는 절차이므로 Codex에서도 사용할 수 있습니다. **Claude 플러그인 설치와 Codex 스킬 등록은 별개**입니다. 현재 Codex 세션의 스킬 목록에서 등록 여부를 확인하고, 미등록 상태에서는 실제 설치된 원본 `SKILL.md`를 명시해 읽고 수행하게 할 수 있습니다. 반복 사용을 위한 Codex 등록·설치 연결은 공용 도구 저장소에서 관리하며 이 하네스에 스킬 본문을 복제하지 않습니다.

gg-tools의 원본은 `~/claude/gg-skills/skills/second-brain/wiki-{ingest,query,lint}/SKILL.md`입니다. 예시는 설치 경로에 맞춰 바꾸고 **위키 저장소에서** 실행합니다.

```text
~/claude/gg-skills/skills/second-brain/wiki-query/SKILL.md를 읽고, 현재 위키의 WIKI_SCHEMA.md 규칙에 따라 [질문]에 답해줘. 근거 페이지를 인용해줘.
```

- `ingest`: 지정한 원본을 통합하고 index·log를 갱신합니다. `raw/`는 읽기만 합니다.
- `query`: 근거 페이지를 인용해 답합니다. 조회만 할 때는 파일을 바꾸지 않고, 답변 저장은 승인받습니다.
- `lint`: 점검 결과를 보고하고, 수정·이동 등은 스키마의 승인 규칙을 따릅니다.
- 위키의 로컬 `AGENTS.md`·`CLAUDE.md`와 `WIKI_SCHEMA.md`를 먼저 읽고 승인·민감정보·커밋 규칙을 지킵니다. Claude의 세션 시작 hook이나 플러그인 명령은 Codex에서 자동 실행되지 않습니다. 필요한 대기 원본 확인 등은 요청에 맞춰 직접 수행합니다.

절차를 읽을 수 있다는 사실과 실제 ingest·자동 호출 검증은 구분합니다. Codex에 등록한 뒤에는 새 세션에서 호출·작은 샘플·결과 확인으로 검증합니다.

### 개인 브레인 vs 프로젝트 브레인 (시험적)

> **표준 관행이 아닙니다.** Karpathy의 LLM Wiki 아이디어를 응용한 새 패턴이라 효과가 검증되지 않았습니다. **필요 없으면 생략해도 됩니다.** 써 보고 안 읽히면 `_brain/`를 지우면 됩니다.

지식 저장소를 2층으로 나눕니다.

| 층 | 자리 | 담는 것 | 에이전트가 읽는 때 |
|---|---|---|---|
| 개인 브레인 | `~/second-brain` (비공개 레포) | 프로젝트와 무관한 지식: 강의·도구·일하는 방식·프로젝트 간 교훈 | 개인 브레인 폴더에서 열 때 |
| 프로젝트 브레인 | 그 레포의 `_brain/` | 그 프로젝트 전용: 결정 이유, 도메인 규칙, 장애 회고, 슬랙·회의록 정리 | 그 레포에서 일할 때 자동(`CLAUDE.md` 포인터) |

**언제 어디에 넣나**

- 다른 프로젝트에서도 쓸 내용인가 → 개인 브레인. 이 프로젝트에서만 의미가 있나 → 프로젝트 브레인.
- 이미 Spec·ADR·PRD·Linear에 있는 내용은 **어느 위키에도 복사하지 않고 링크만** 합니다. 위키에는 "그 결정이 나온 맥락"처럼 정본에 없는 것만 씁니다.
- 위키 내용이 오래 유효해지면 `docs/`의 정본으로 올립니다(위 승격 규칙).

**슬랙·회의록을 넣는 법**

- 채널 전체를 통째로 넣지 않습니다. **의사결정이 있었던 스레드·회의만** 골라 마크다운으로 정리해 `_brain/raw/`에 두고 "위키에 넣어"라고 합니다. **5~10개로 시작**해서 쓸모를 본 뒤 늘립니다.

**민감 정보 규칙**

- 개인정보·인증정보·고객 데이터·인사·보안 사고는 위키에도 `raw/`에도 넣지 않습니다. 이름·연락처·금액·계정은 지우고 옮깁니다.
- `_brain/raw/`는 `.gitignore`로 git 이력에서 제외하고, 정리된 `_brain/wiki/` 페이지(`index.md` 등)만 커밋합니다.

뼈대와 규칙은 [`_brain/WIKI_SCHEMA.md`](../../_brain/WIKI_SCHEMA.md)에 있고, 4장의 `wiki-*` 스킬이 같은 구조로 동작합니다. 스킬(wiki-ingest 등)은 wiki-template 구조를 기준으로 하므로 `_brain/` 안에서도 `raw/` 와 `wiki/` 2층을 유지합니다.

### PR 위험 5축

PR 양식의 "예상 위험"에 아래를 한 줄씩 적습니다: **보안 · 변경 범위 · 하위 호환 · 테스트 커버리지 · 마이그레이션**.

### AI 교체·새 세션 인계

AI를 바꾸거나 작업 경계에서 새 세션을 시작할 때, 같은 탐색·계획·수정을 반복할 때만 인계합니다. 매 답변마다 작성하지 않습니다. 기본은 채팅의 짧은 인계문이며, 저장 요청이 있을 때만 `.artifacts/`의 git 제외 임시 파일에 보관합니다.

```text
목표 / 완료 조건:
확정 결정 / 승인 범위(금지 범위 포함):
현재 Issue / 관련 정본·기존 계획 링크:
작업 디렉터리·브랜치 / 변경 파일·사용자 WIP:
검증 명령·fresh 결과·확인 시점:
미해결 질문 / 이어서 확인할 사항:
```

진행률·일정·우선순위·Backlog를 복제하지 않습니다(Linear가 정본). 인계문은 확인 시점의 참고 자료이며 실행 보드가 아닙니다. 비밀정보·운영 고객 데이터·전체 대화 로그를 넣지 않습니다. 다음 AI는 브랜치·Git 상태·관련 파일을 재확인하고, 기존 결정을 다시 설계하지 않되 충돌하는 증거가 있으면 보고합니다. 오래된 검증 결과는 현재 통과 근거로 사용하지 않습니다.

### 실제 실행 환경과 권한 확인

권한 오류가 난 프로세스의 시작 명령·실행 옵션·로그에서 sandbox와 approval 설정을 확인합니다. companion이 실행 시 전달한 옵션은 전역 config와 다를 수 있으므로, 전역 설정이나 다른 프로세스의 성공 기록으로 실패 원인을 판단하지 않습니다. 확인한 실행 옵션과 오류를 비밀정보 없이 짧게 남깁니다.

승인 요청이 허용되는 런타임은 정상 권한 요청을 사용하고, 금지되는 런타임은 실패 원인과 필요한 실행 환경을 보고합니다. 보호 수단을 끄거나 금지된 옵션을 재시도하지 않습니다. companion 명령·옵션·런타임의 정본은 해당 외부 플러그인이고, Superpowers의 스킬 본문도 외부 소유입니다. 이 문서는 프로젝트 계약과 확인 기준만 연결하며 엔진·스킬·별도 실행기를 복사하지 않습니다.

### 느리거나 방향을 잃었을 때

느린 사례 한 건의 요청 시각·첫 응답 시각·끝난 시각과 세션 식별자를 기록하고, 사용 도구가 제공하는 로그로 다음을 구분합니다. 로그 전체를 자동 수집하거나 외부로 전송하지 않습니다.

| 구간 | 확인할 근거 | 대응 |
|---|---|---|
| 응답 대기 | 첫 응답까지의 시간, 실행 기록 유무 | 원인을 추측하지 않고 기록. 필요하면 같은 범위의 요청을 새 세션에서 비교 |
| 도구 실행 | 명령과 시작·종료 시각, 오류 | 범위를 좁히고 진행 여부를 확인. 살아 있는 테스트를 임의 종료하지 않음 |
| hook 대기 | 해당 hook의 실행 기록과 소요 시간 | Claude hook인지 확인하고 소유 저장소에서 별도 수정. 안전 hook 비활성화로 우회하지 않음 |
| 반복 작업 | 같은 파일 탐색·계획·검증을 반복한 기록 | 목표·결정·근거를 인계해 새 세션에서 이어감 |

확인할 수 없는 시간은 `미확인`으로 남깁니다. ‘생각 중’ 표시는 원인 판정의 근거가 아닙니다. 도구 작업 중에는 발견·다음 확인·막힌 이유를 짧게 알리되, 모델 응답 자체를 기다리는 동안의 주기적 안내는 보장하지 않습니다. 긴 대화와 새 세션 비교는 단서이며 모델·서비스·요청 차이를 통제하지 않은 결과를 속도 개선 수치로 단정하지 않습니다.
