# 2. 하루 루프와 세컨드 브레인

> **목적:** 이 레포를 받은 뒤 **채팅으로 말하면서 바로 개발**하는 일상 방식을 정합니다. 스킬과 hook은 이 레포에 복사하지 않고 **gg-tools 플러그인에서 가져다 씁니다**(소유권은 [gg-tools README](https://github.com/gggmlduswjs/gg-tools#자산-소유권--먼저-여기서-확인) 기준).
> 일반적인 AI 개발 방식에서 이 틀에 필요한 것만 골랐습니다.

## 1. 한 줄 원칙

**수집은 AI가, 판단은 사람이, 실행은 다시 AI가 합니다.**
사람이 판단하는 지점은 이미 틀에 들어 있습니다: PRD·ROADMAP·ARCHITECTURE 승인, 설계서 승인, 계획서 승인, 머지 승인, Done 증거 확인.

## 2. 하루 루프

| 시간 | 하는 일 | 쓰는 것 |
|---|---|---|
| 아침 | 오늘 할 일 파악 | Linear 뷰 **지금**·**다음**, 아래 브리핑 프롬프트 |
| 낮 | 이슈 하나의 관련 문서·코드 확인 → 구현 → 관련 검증. 중요한 불확실성에는 조사, 복잡하거나 고위험인 작업에는 설계·계획 추가 | 작업 위험도에 맞는 superpowers 흐름([0-start-project.md](0-start-project.md) 8단계) |
| 낮 | 결과를 검수하고 재지시 | 계획 검토 4체크(5장), 테스트, PR diff |
| 저녁 | 한 일·못한 일·개선점 정리 | Linear 뷰 **증거 대기**, 세컨드 브레인 기록(4장) |

**브리핑 프롬프트** (스킬 없이 그대로 붙여 쓰는 한 줄 요청):

```text
Linear에서 내게 할당된 이슈 중 In Progress와 Todo를 우선순위순으로 정리해줘.
머지 안 된 PR과 main의 CI 상태도 확인해서, 오늘 꼭 할 일과 안 해도 될 일을 나눠줘.
```

반복해서 길어지면 그때 gg-tools에 스킬로 올립니다(이 레포에는 두지 않음).

## 3. 처음 한 번 설정 — 플러그인 연결

**Team Plugin**(스킬·hook·명령을 한 묶음으로 배포하는 단위)이 우리에게는 [gg-tools](https://github.com/gggmlduswjs/gg-tools)의 `gg-skills` 플러그인입니다. 이 레포 `.claude/settings.json`은 **어떤 플러그인을 쓰는지 선언**만 합니다(superpowers, gg-skills). 스킬 파일은 레포에 없습니다. 새 PC에서는 한 번만 실행합니다.

```powershell
gh repo clone gggmlduswjs/gg-tools ~/claude
pwsh ~/claude/bootstrap.ps1
```

이후 Claude Code를 새 세션으로 열면 됩니다. 자동 검사 hook(위험 명령 차단)의 shim은 [`.claude/hooks/guardrail.py`](../../.claude/hooks/guardrail.py)이고, 판정 로직은 gg-tools 엔진 한 벌입니다. 엔진이 없는 PC에서는 조용히 통과하지 않고 **확인을 요청**합니다(보호가 꺼진 것을 숨기지 않기 위해).

| 하고 싶은 것 | 쓰는 것 (gg-skills) |
|---|---|
| 틀을 적용한 뒤 AI가 코드를 잘 이해하는지 점수 | `ai-readiness-cartography` |
| 하네스 빈칸 점검 | `harness-audit` |
| 토큰·비용 점검 | `improve-token-efficiency` |
| 보안 점검 | `owasp-security-scan` |
| 세컨드 브레인 (선택) | `wiki-ingest` · `wiki-query` · `wiki-lint` (외부 `agentic-eng-toolkit`) |

## 4. 지식이 사는 곳 — 세컨드 브레인

세컨드 브레인에 **기준 문서를 두면 정본이 하나 더 생깁니다.** 그래서 층을 나눕니다.

| 층 | 담는 것 | 정본인가 |
|---|---|---|
| Repo `docs/` | 제품·설계·결정·업무 규칙 | **예 (지식)** |
| Linear | 진행·우선순위·일정 | **예 (실행)** |
| 자동 메모(Auto-memory) | AI에게 알려 준 개인 선호 | 개인용 |
| 세컨드 브레인 (`second-brain` 레포) | 여러 프로젝트에서 재사용하는 일반 지식, 강의·조사 요약 | **아니오.** 프로젝트 정본을 링크만 함 |

팀이 공유할 규칙은 `CLAUDE.md`, 개인 선호는 자동 메모입니다.

**승격:** 세컨드 브레인의 메모가 프로젝트에 유효해지면 `.dev/research/` → `docs/` 순으로 올립니다([CONVENTIONS](../CONVENTIONS.md) 6장). **복사하지 말고 한 곳으로 옮기고 링크**합니다.

### 어디에 두나 — 별도 비공개 레포 `second-brain`

| 지식의 종류 | 자리 |
|---|---|
| 한 프로젝트에서만 쓰는 지식 | **그 프로젝트의 정본 자리**(보통 그 프로젝트 레포의 `docs/`). 정본이 레포 밖(예: 별도 문서 폴더)에 있으면 그 자리를 그대로 존중하고, 여기로 복사하지 않음 |
| 여러 프로젝트에서 다시 쓰는 일반 지식 | **`second-brain` 레포** (GitHub 비공개, 로컬 `~/second-brain`) |
| AI가 건드리지 않는 개인 노트(일정, 인박스, 공부) | 구글 드라이브 Obsidian |

구글 드라이브에는 변경 이력이 없고 동기화 지연·충돌이 있어서, 새로 쌓는 AI 위키는 **git 레포**에 둡니다. Obsidian은 이 폴더를 볼트로 열면 됩니다. 같은 지식이 여러 곳에 있으면 정본이 둘 생기므로, 위 표의 첫 줄(프로젝트 전용은 프로젝트 정본)을 먼저 지킵니다. 낡은 위키는 지우지 않고 `_archive/`로 보관하며 근거로 쓰지 않습니다.

### 구조 (3층)

`agentic-eng-toolkit` 플러그인의 `wiki-*` 스킬이 기대하는 구조이고(빈 틀은 [wiki-template](https://github.com/gggmlduswjs/wiki-template) 저장소의 **Use this template**로 만듭니다), 프로젝트 안에 둔 위키도 같은 구조를 쓰면 같은 스킬이 동작합니다.

```text
second-brain/
├── WIKI_SCHEMA.md   ← 규칙: 파일명·프론트매터·본문 틀·Ingest/Query/Lint   (Schema, 스킬이 가장 먼저 읽음)
├── raw/             ← 원문. 사람이 넣고 수정하지 않음                      (Raw)
├── wiki/
│   ├── index.md     ← 카탈로그 (페이지마다 한 줄 요약)
│   ├── log.md       ← 추가만 하는 기록 ([INGEST] [QUERY] [LINT] [MOVE])
│   └── concepts/ people/ tools/   ← 페이지, [[링크]]로 연결
└── _archive/        ← 낡은 기록
```

- **넣기:** 원문을 `raw/`에 두고 "위키에 넣어"라고 하면 `wiki-ingest`가 통합하고 `index.md`·`log.md`를 갱신합니다.
- **묻기:** "위키에서 찾아"라고 하면 `wiki-query`가 `[[페이지]]`를 인용해 답합니다.
- **점검:** 가끔 `wiki-lint`로 모순·고아 페이지·깨진 링크를 찾습니다(고치기 전에 승인).
- 마크다운과 `[[링크]]`를 쓰므로 Obsidian으로 열어 볼 수 있습니다.

> 첫 Ingest는 `SKILL.md` 절차대로 수동으로 시험해 통과했습니다(페이지 3개, 깨진 링크 0). 스킬 자동 호출은 새 세션에서 따로 확인합니다. 스킬은 폴더를 만들지 않으므로 위키 폴더(`WIKI_SCHEMA.md`가 있는 곳)에서 Claude Code를 열어 시작합니다.

### 개인 브레인 vs 프로젝트 브레인 (시험적)

> **표준 관행이 아닙니다.** Karpathy의 LLM Wiki 아이디어를 응용한 새 패턴이라 효과가 검증되지 않았습니다. **필요 없으면 생략해도 됩니다.** 써 보고 안 읽히면 `_brain/`를 지우면 됩니다.

지식 저장소를 2층으로 나눕니다.

| 층 | 자리 | 담는 것 | 에이전트가 읽는 때 |
|---|---|---|---|
| 개인 브레인 | `~/second-brain` (비공개 레포) | 프로젝트와 무관한 지식: 강의·도구·일하는 방식·프로젝트 간 교훈 | 개인 브레인 폴더에서 열 때 |
| 프로젝트 브레인 | 그 레포의 `_brain/` | 그 프로젝트 전용: 결정 이유, 도메인 규칙, 장애 회고, 슬랙·회의록 정리 | 그 레포에서 일할 때 자동(`CLAUDE.md` 포인터) |

**언제 어디에 넣나**

- 다른 프로젝트에서도 쓸 내용인가 → 개인 브레인. 이 프로젝트에서만 의미가 있나 → 프로젝트 브레인.
- 이미 Spec·ADR·PRD·Linear에 있는 내용은 **어느 위키에도 복사하지 않고 링크만** 합니다. 위키에는 "그 결정이 나온 맥락"처럼 정본에 없는 것만 씁니다.
- 위키 내용이 오래 유효해지면 `docs/`의 정본으로 올립니다(위 승격 규칙).

**슬랙·회의록을 넣는 법**

- 채널 전체를 통째로 넣지 않습니다. **의사결정이 있었던 스레드·회의만** 골라 마크다운으로 정리해 `_brain/raw/`에 두고 "위키에 넣어"라고 합니다. **5~10개로 시작**해서 쓸모를 본 뒤 늘립니다.

**민감 정보 규칙**

- 개인정보·인증정보·고객 데이터·인사·보안 사고는 위키에도 `raw/`에도 넣지 않습니다. 이름·연락처·금액·계정은 지우고 옮깁니다.
- `_brain/raw/`는 `.gitignore`로 git 이력에서 제외하고, 정리된 `_brain/wiki/` 페이지(`index.md` 등)만 커밋합니다.

뼈대와 규칙은 [`_brain/WIKI_SCHEMA.md`](../../_brain/WIKI_SCHEMA.md)에 있고, 4장의 `wiki-*` 스킬이 같은 구조로 동작합니다. 스킬(wiki-ingest 등)은 wiki-template 구조를 기준으로 하므로 `_brain/` 안에서도 `raw/` 와 `wiki/` 2층을 유지합니다.

## 5. 일하는 습관 5가지

| # | 습관 | 이 틀에서의 규칙 |
|---|---|---|
| 1 | 짧은 세션 | 한 세션 = 한 작업. 작업 경계·AI 교체·반복 탐색 시 아래 인계문으로 새 세션에서 이어감. Claude의 `/compact`는 진행 중 문맥 정리 선택지 |
| 2 | `CLAUDE.md`를 살려 둠 | **100~200줄 이하.** 매 세션 꼭 알아야 하는 것만 두고 나머지는 `docs/`로 링크 |
| 3 | 계획을 받으면 4가지 확인 | 아래 표 |
| 4 | AI 출력 검증 | 관련 테스트 + PR diff(특히 **삭제된 코드**) + CI. 독립 AI 리뷰는 고위험·복잡한 작업에 추가 |
| 5 | 메모리와 `CLAUDE.md` 구분 | 팀 규칙은 `CLAUDE.md`, 개인 선호는 자동 메모 |

### 계획 검토 4체크 (계획서 승인 전 2~3분)

| 체크 | 물어볼 것 | 나쁜 신호 |
|---|---|---|
| 수정 범위 | 요청 이상으로 파일을 건드리나 | "필드 하나 추가"인데 전체 리팩토링 |
| 기존 패턴 | 이미 있는 것을 쓰나 | 같은 역할의 서비스를 새로 만듦 |
| 테스트 | 테스트가 계획에 들어 있나 | "코드 먼저, 테스트는 나중에" |
| 리스크 | 마이그레이션·하위 호환·데이터 손실·성능을 짚었나 | 스키마 변경인데 마이그레이션 단계 없음 |

### PR 위험 5축

PR 양식의 "예상 위험"에 아래를 한 줄씩 적습니다: **보안 · 변경 범위 · 하위 호환 · 테스트 커버리지 · 마이그레이션**.

### AI 교체·새 세션 인계

AI를 바꾸거나 작업 경계에서 새 세션을 시작할 때, 같은 탐색·계획·수정을 반복할 때만 인계합니다. 매 답변마다 작성하지 않습니다. 기본은 채팅의 짧은 인계문이며, 저장 요청이 있을 때만 `.artifacts/`의 git 제외 임시 파일에 보관합니다.

```text
목표 / 완료 조건:
현재 Issue와 관련 정본 링크:
확정 결정과 승인 범위:
브랜치 / 변경 파일 / 사용자 WIP:
검증 명령·결과·확인 시점:
미해결 질문 / 이어서 확인할 사항:
```

진행률·일정·우선순위·Backlog를 복제하지 않습니다(Linear가 정본). 인계문은 확인 시점의 참고 자료이며 실행 보드가 아닙니다. 비밀정보·운영 고객 데이터·전체 대화 로그를 넣지 않습니다. 다음 AI는 브랜치·Git 상태·관련 파일을 재확인하고, 기존 결정을 다시 설계하지 않되 충돌하는 증거가 있으면 보고합니다. 오래된 검증 결과는 현재 통과 근거로 사용하지 않습니다.

### 느리거나 방향을 잃었을 때

느린 사례 한 건의 요청 시각·첫 응답 시각·끝난 시각과 세션 식별자를 기록하고, 사용 도구가 제공하는 로그로 다음을 구분합니다. 로그 전체를 자동 수집하거나 외부로 전송하지 않습니다.

| 구간 | 확인할 근거 | 대응 |
|---|---|---|
| 응답 대기 | 첫 응답까지의 시간, 실행 기록 유무 | 원인을 추측하지 않고 기록. 필요하면 같은 범위의 요청을 새 세션에서 비교 |
| 도구 실행 | 명령과 시작·종료 시각, 오류 | 범위를 좁히고 진행 여부를 확인. 살아 있는 테스트를 임의 종료하지 않음 |
| hook 대기 | 해당 hook의 실행 기록과 소요 시간 | Claude hook인지 확인하고 소유 저장소에서 별도 수정. 안전 hook 비활성화로 우회하지 않음 |
| 반복 작업 | 같은 파일 탐색·계획·검증을 반복한 기록 | 목표·결정·근거를 인계해 새 세션에서 이어감 |

확인할 수 없는 시간은 `미확인`으로 남깁니다. ‘생각 중’ 표시는 원인 판정의 근거가 아닙니다. 도구 작업 중에는 발견·다음 확인·막힌 이유를 짧게 알리되, 모델 응답 자체를 기다리는 동안의 주기적 안내는 보장하지 않습니다. 긴 대화와 새 세션 비교는 단서이며 모델·서비스·요청 차이를 통제하지 않은 결과를 속도 개선 수치로 단정하지 않습니다.

## 6. 하지 않는 것

| 일반적으로 쓰는 것 | 이 틀에서는 |
|---|---|
| 출근길 메신저 자동 브리핑(cron) | 설정이 크고 1인 개발에 과함. 필요해지면 gg-tools에 추가 |
| Context Intelligence (조직 전체 인덱싱) | 팀 규모가 될 때 |
| Oncall agent | ROADMAP의 운영 단계(On-call)에서 |
